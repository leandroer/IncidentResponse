INCIDENT MODE

Use this page to make the next defensible decision

Start here when an alert is credible, impact may be active, or short-retention evidence is at risk. Product output is a lead; the incident record is the evidence.

Trigger

Credible malicious activity, unauthorized access, destructive behavior, material data exposure, or unsafe automation requiring coordinated response.

First five actions

  1. Assign incident lead, technical lead, scribe, severity, and UTC time basis.
  2. Preserve the original alert and the shortest-retention evidence.
  3. Identify affected identities, assets, services, data, and trust boundaries.
  4. Present containment choices with authority, impact, rollback, and validation.
  5. Record every state-changing action and confirm its result independently.

Evidence to preserve

Original alerts, raw telemetry, audit logs, process lineage, sessions, configuration state, volatile data, hashes, collector details, and an operator action log.

Authority and exit criteria

Get explicit authority for service disruption, isolation, identity restriction, evidence acquisition, disclosure, and destructive remediation. Exit incident mode only when active impact is stopped, scope is bounded, evidence is protected, and recovery owners accept the residual risk.

Selection principle

Choose tools for the evidence source and decision at hand. Preserve original telemetry, record collection time and operator actions, and validate automated findings before containment or eradication.

ROUTING

Choose the incident path, not a product

Each route starts with a decision, an evidence package, and a containment safeguard.

Ransomware or destructive activity

Start with: active encryption, identity, management-plane, backup, and egress evidence.

Open ransomware playbook · Containment matrix

Identity compromise

Start with: sessions, authentication methods, privilege changes, application grants, and persistence.

Open identity playbook · Investigation worksheet

Cloud or SaaS compromise

Start with: identity, control-plane, workload, network, and application audit records.

Open cloud/identity route · Cloud evidence checklist

Data exposure or exfiltration

Start with: repository, owner, data class, access path, identity, destination, time window, and volume.

Open data-exposure playbook · Reporting coordination

Malware outbreak

Start with: process lineage, persistence, delivery path, network behavior, affected assets, and variants.

Open malware playbook · Analysis resources

Repository or supply-chain compromise

Start with: Git history, audit events, workflows, identities, dependencies, artifacts, and signing state.

Open repository response · Repository checklist

AI or agent incident

Start with: instructions, model/version, traces, tools, retrieval, memory, identities, and downstream actions.

ENGINEERING

Detection engineering

Represent behavior as portable logic, test it against real telemetry, and track coverage.

Decision supported: whether observed behavior is repeatable, detectable, and material to this incident.

Confirm with: raw source telemetry and an affected-system timeline—not a rule match alone.

State-change caution: test new logic against representative data before enabling automated response.

TELEMETRY

Network, cloud, SaaS, and containers

Collect control-plane, identity, workload, packet, and application evidence as a single incident timeline.

Decision supported: whether malicious activity crossed trust boundaries, changed control-plane state, or reached data and workloads.

Confirm with: identity, endpoint, and application-level transactions.

State-change caution: network blocks and cloud-policy changes can affect shared services, recovery access, and evidence collection.

Network

  • Wireshark — packet-level inspection; captures may contain credentials and regulated data.
  • Zeek — structured network metadata and protocol analysis.
  • Suricata — IDS/IPS, protocol logging, and rule-based detection.

Cloud and SaaS

  • Microsoft Defender for Cloud — posture and workload protection across Azure, AWS, and Google Cloud.
  • AWS CloudTrail and GuardDuty — control-plane evidence and managed threat detection.
  • Google Security Command Center — cloud findings, posture, and threat detection.
  • Microsoft Purview Audit — Microsoft 365 user and administrative activity.

Containers and Kubernetes

  • Microsoft Defender for Containers — multicloud Kubernetes posture, image vulnerability assessment, and runtime threat protection.
  • Falco — runtime detection using kernel and Kubernetes signals.
  • Trivy — image, filesystem, configuration, and SBOM assessment.
  • Kubernetes audit logs — API activity and control-plane evidence.
EVIDENCE

Forensics and evidence collection

Use targeted triage first, then escalate to full acquisition when scope, legal hold, or investigative depth requires it.

Decision supported: what happened, when, through which identity or system, and with what evidentiary confidence.

Confirm with: a second telemetry source, acquisition hashes, and documented collection context.

State-change caution: collection changes the source; record tool, version, operator, UTC time, method, and resulting state.

Evidence discipline

Record the source, collector, UTC timestamps, acquisition method, tool version, cryptographic hash, storage location, and every transfer. Avoid changing system state unless the response decision justifies it and the action is recorded.

ANALYSIS

Malware analysis

Separate initial classification, dynamic behavior, and reverse engineering. Never treat a single scanner verdict as conclusive.

Decision supported: what the artifact can do, whether it executed, and which behavioral indicators should drive the hunt.

Confirm with: sandbox or reverse-engineering results plus telemetry from the affected environment.

State-change caution: analyze in an isolated environment and never submit sensitive material to a public service without authorization.

Public-service handling warning

Before submitting a file, URL, packet capture, document, or indicator to a public analysis service, confirm the organization’s data-handling policy. Public or community submissions may become accessible to vendors, researchers, or other service users. Use private analysis, contractual controls, or an isolated internal sandbox for sensitive material.

  • VirusTotal — multi-engine enrichment and relationship analysis; submission visibility depends on service and license.
  • ANY.RUN — interactive dynamic analysis; verify privacy mode before uploading.
  • capa — identifies executable capabilities from static or dynamic evidence.
  • Ghidra and IDA Pro — disassembly and reverse engineering.
  • CAPE Sandbox — self-hosted automated malware analysis and configuration extraction.
